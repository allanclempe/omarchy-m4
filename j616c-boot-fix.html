Omarchy on Apple silicon · M4 Max bring-up

J616c: a clean Omarchy install with no hand steps

MacBook Pro 16" M4 MaxMac16,5 · J616c · T60412026-11-13 to 11-16

Omarchy runs on the M4 Max MacBook Pro: Hyprland desktop, all 14 CPU cores, Aurora's GPU driver, Wi-Fi, audio and the light sensor. The first install on 11-14 needed hand fixes at five stages. All of them are now in the build. A clean install on 11-16 needed no typed command, edit or extra package, through install, first boot, owner setup and the first omarchy update. That reinstall also showed that the J616c has to boot aura's raw Stage 1, not a Mach-O one.

The reinstall's finding

The T6041 boots aura's raw Stage 1

On the first install, the unpadded Mach-O object booted Linux. On the clean reinstall, the installer enrolled that object, and aura's Stage 2 refused:

“CTXR exec: CPU 0 could not run the heap probe (ESR 0x8600000c): secondaries are confined at EL2 … the secondary CPUs can only run code in a window, and there is none for the OS: this Stage 1 did not arm a large enough window. Not starting the OS.”

aura Stage 2 94d8e6e, on the J616c, 2026-11-16

The same refusal came with the b13 object that had booted the first install, with the first install's Stage 2 image, and with aura-proxy on the ESP. Why the first install booted is unknown, because its boot policy was never recorded. aura's docs describe the refusal as designed. They also give the way out: with a raw Stage 1, Kernel CTRR is not enabled, and a raw Stage 1 enrolled with it off boots with the secondary CPUs free.

So the installer now runs bputil -nc, then kmutil configure-boot --raw --entry-point 2048 --lowest-virtual-address 0. That is Omarchy's stock raw mode for M1 to M3, but chainloading m1n1/boot-ctxr.bin, the file Aurora's update-m1n1 writes on T6041. Linux comes up on all 14 cores, unconfined. The cost is the execute window: no hibernation layout and none of aura's EL2 features that need it.

The first fix

aura b13's Stage 2 never restarts a powered-off ANS

On M4 and later, aura's Stage 1 powers ANS off after reading Stage 2 from the ESP and passes the controller's SART entries on as nvme.sart=. Aurora fixed Stage 2 in aaec599f on 2026-11-13:

“An ESP Stage 2 that boots its embedded U-Boot never runs nvme_init(): it only writes the entries to the DT as apple,sart-entries and leaves ANS off. The U-Boot we embed adopts a running post-M4 ANS and can't start one from off, so with a Stage 1 that passes nvme.sart= it fails to probe NVMe.”

aurora-silicon/aura aaec599f · payload: start a post-M4 ANS an earlier stage powered off before any payload

1.0.0b13 (f0f180af) lacks it. 1.0.0b13.1, cut from a release branch, carries the identical change as 564efba5. We missed that at first and pinned Stage 2 to aura 94d8e6e, built with the PKGBUILD's flags (RELEASE=1 CHAINLOADING=1 ESP_STAGE2=1 USE_CLANG=1 BUILTIN_LOGO=aurora). The image still carries that pin; dropping it is next.

On the first install the new Stage 2 went onto the ESP by hand. macOS 26.7.3 couldn't mount any FAT volume on this Mac, so a script overwrote the same-size file's clusters in place, after checking the label, both FATs and the old hash.

Findings along the way

Things the team should know

The shared ESP serial hits one-install Macs too

Every install's ESP is 4F4D-5801 and every Boot partition shares one UUID. A single install plus an earlier attempt's leftover partitions is enough to mount the wrong ones. Added to omarchy-mac-installer#219.

The USB proxy can't test the ANS hand-off

With aura-proxy on the ESP, Stage 1 powers ANS off before waiting for a host, and chainload.py doesn't pass nvme.sart=. A Stage 2 sent over USB never sees the state a real boot gives it. Test this path from the ESP.

The kernel was never the blocker

The image uses Aurora Silicon's linux-aurora 7.3.0.aurora1-40, pinned with its Mesa. When checked on 11-14, omacom/linux-aurora (bed544bd) had no T604x device trees. The kernel and its Mesa have to come as a matching pair.

Wi-Fi works

wlan0 comes up with the BCM4388 firmware collected from macOS. That depends on our fix for PR #212's chflags bug, where shutil.copytree fails with EPERM on SIP-restricted files.

Asks

What's left, per team

  1. omarchy-mac-pkgs: review #150, the boot check for Aurora's Stage 2. Once it ships, the image drops its owner-managed marker.
  2. Installer: fix the shared IDs (#219). Teach the app's Remove to recognise aura's boot object: it refuses every M4 install today. The J616c's raw-ctxr mode, the IMX958 camera setfile in the registry, and the #212 chflags fix are in patches/j616c-installer.patch, ready to propose.
  3. Aurora: report the padded Stage 1's silent loop on T6041, with the object their own tool makes. Ask for a documented dry-run that prints the Stage 2 update-m1n1 would build, so the boot check needn't load bootchain_arch.py.
  4. Kernel: the J616c needs a kernel with the T6041 device trees, and its matching Mesa, on the channel Omarchy ships.
  5. Our image: drop the Stage 2 pin, now that aura 1.0.0b13.1 has the ANS fix. Set the app version in the build script instead of by hand. The Stage 2 trial path hasn't run yet: it waits for the next boot-chain update.
