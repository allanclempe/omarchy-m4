J616c: Omarchy boots to the desktop

MacBook Pro 16" M4 MaxMac16,5 · J616c · T60412026-11-13 to 11-14

Omarchy now runs on the M4 Max MacBook Pro: Hyprland desktop, all 14 CPU cores, Aurora's GPU driver and Wi-Fi. Getting there took four fixes after the install itself. Three are bugs in our J616c image build and one is in the installer. Each is described below with its evidence, so the image can be rebuilt to boot without hand fixes.

The main fix

aura b13's Stage 2 never restarts a powered-off ANS

On M4 and later, aura's Stage 1 powers ANS off after reading Stage 2 from the ESP and passes the controller's SART entries on as nvme.sart=. Aurora fixed Stage 2 in aaec599f on 2026-11-13:

“An ESP Stage 2 that boots its embedded U-Boot never runs nvme_init(): it only writes the entries to the DT as apple,sart-entries and leaves ANS off. The U-Boot we embed adopts a running post-M4 ANS and can't start one from off, so with a Stage 1 that passes nvme.sart= it fails to probe NVMe.”

aurora-silicon/aura aaec599f · payload: start a post-M4 ANS an earlier stage powered off before any payload

Neither 1.0.0b13 (f0f180af, in our image) nor 1.0.0b13.1 (5dcf62d0, cut from a release branch) contains it. We built Stage 2 from aura 94d8e6e with the PKGBUILD's flags (RELEASE=1 CHAINLOADING=1 ESP_STAGE2=1 USE_CLANG=1 BUILTIN_LOGO=aurora) and swapped it into boot-ctxr.bin. The device tree and U-Boot in that file are unchanged, byte for byte.

Findings along the way

Things the team should know

All 14 cores without the padded Stage 1

aura's docs say an OS outside the CTXR_D window gets only the boot CPU. On this J616c, Linux brought up all 14 cores (0-13) with the unpadded object. That makes the padded loop less urgent for J616c, and it's worth telling Aurora.

The USB proxy can't test the ANS hand-off

With aura-proxy on the ESP, Stage 1 powers ANS off before waiting for a host, and chainload.py doesn't pass nvme.sart=. A Stage 2 sent over USB never sees the state a real boot gives it. Test this path from the ESP.

The kernel was never the blocker

The image uses Aurora Silicon's linux-aurora 7.3.0.aurora1-36. omacom/linux-aurora (bed544bd) has no T604x device trees, so it can't boot J616c yet. The kernel and its Mesa have to come as a matching pair.

Wi-Fi works

wlan0 comes up with the BCM4388 firmware collected from macOS. That depends on our fix for PR #212's chflags bug, where shutil.copytree fails with EPERM on SIP-restricted files.

Asks

Proposed next steps

  1. J616c image (tools/derive-j616c-image): take Stage 2 from aura with aaec599f. Install mesa-aurora and vulkan-aurora from [aurora] along with the kernel. Make first boot trust Aurora's key (add aurora to the populated keyrings), or don't leave [aurora] enabled.
  2. Installer: give each ESP a unique FAT serial, or have fstab mount /boot/efi by PARTUUID. Otherwise a reinstall without a prior Remove mounts the wrong ESP. Also report the #212 chflags bug, and add a Mach-O Stage 1 mode (Recovery only does raw today).
  3. Aurora: ask for an aura release with aaec599f. Report the padded Stage 1 silent loop on J616c (T6041), and that the unpadded object still gives 14 cores.
  4. Kernel: ask whether omacom/linux-aurora will carry T6041 device trees. Until then J616c needs Aurora's kernel and Mesa.
  5. This Mac: fstab now mounts /boot/efi by PARTUUID=272043e7-…-93d6-…. The first attempt's partitions (disk0s7 to disk0s10) are still to be removed from macOS. The update guards (no Stage 2 rebuilds, kernel and Mesa held) stay until an aura release contains aaec599f.

Undo and reproduce

All paths below are in the allanclempe/omarchy-m4 repo. To put the original Stage 2 back, run the overwrite script from macOS on a checkout of the repo. Pass the original file (sha256 b6daef1f…8399, kept as a backup when the fix was written) as the new file, and swap the two hashes:

sudo /usr/bin/python3 -I tools/esp-overwrite-same-size.py /dev/rdisk0s4 \
  m1n1/boot-ctxr.bin ORIGINAL-boot-ctxr.bin \
  --label "EFI - OMARC" \
  --expect-old a0f493b491a896c32530f18d0d2320bda210881ef3274de5529b78c2ef9ff552 \
  --expect-new b6daef1f655777fea3ef3f6b62d3c6c7ccad36f8149ee09d433d10fa06898399 \
  --backup boot-ctxr.bin.ansfix --write
